# 从数模到产品：只围绕 V2 故障这件事

## 用户与流程

主要用户是配送中心的调度员。每天早上拿到当天订单、车辆和门店收货规则，先做正常计划；司机途中报故障，调度员录入消息，核对结构化事件，查看候选路线与代价，确认后才通知司机。主管用运行记录复盘。网页是让这些决策可见的工作台，算法是做计算的工具，AI 是理解消息和解释计算结果的助手。

实际软件需要保存“计划版本、订单状态、车辆位置、异常事件”，不能每次从头假装所有车还在仓库。当前原型已保存事件、候选计划和采用/撤回记录，但位置仍从模拟初始计划按故障时间推算，尚未接实际状态或 GPS，也未推进已采用后的连续事件。

## 例子

08:25，V2 的 S05/S06 已交付，S07/S08 仍在车上。我们不能撤销已交付订单，也不能让 S07 的货凭空出现在 V1 车上。先确定 V2 故障位置，再算正常车辆何时到那里接货，以及接货后会不会超载。代码输出 V1/V3 的候选配送顺序，页面逐单显示到达时间变化。

## 最小数学模型

订单集合 I，正常车辆集合 K，故障订单集合 F。已完成订单固定。每个订单有货量 q_i、开门时间 a_i、承诺时间 d_i 和最晚收货时间 b_i。车辆容量 Q_k，故障时坐标 p_k，可再次出发时间 t_k，已装货集合 C_k。故障点 p_f，每次接货时间 h。

决策是故障订单分配 y_ik 与每车的访问序列 π_k（含可选接货节点 P）。

1. 每个故障订单只分配给一辆正常车：sum_k y_ik = 1；若无完整可行候选，原型报告未安排，不自动删掉订单。
2. 原正常车已装订单仍由原车配送；已完成订单不参与新分配。
3. 分到车 k 的故障订单 i，必须满足 P 在序列中早于 i。
4. 车 k 初始载重为故障时车上货量；接货时加 sum_i q_i y_ik，送货时减 q_i，任何节点必须 0 ≤ L ≤ Q_k。
5. 到达 T_j = max(a_j, T_i + s_i + distance(i,j)/v)。接货服务时间为 h，送货服务时间为 5；a_j ≤ T_j ≤ b_j。
6. 迟到量 l_i=max(0,T_i-d_i)。迟到单数是 sum_i 1[l_i>0]，不是未安排订单数；两者都报告。
7. 当前按优先级比较（未安排、迟到单数、迟到分钟、成本+扰动惩罚）。不是对所有指标同时最优的承诺。

代码使用小规模枚举来表达上述模型，不是完整的混合整数规划求解器。初始分区固定。恢复时枚举二分分配及顺序，每个分配先保留局部优选，再比较总体指标；局部与整体扰动定义尚有差异，不能宣称全局最优。

## 模型如何进入产品

`engine.py` 管数据、推算位置、检查载重与时间、选候选并统计指标；`server.py` 提供本地接口；`web/` 画图和展示变化。界面不自己编造优化数值。`tests/` 用独立的载重和时间推算核查结果；`benchmark.py` 存下对照证据。

0.2 已完成：事件与计划版本、本地采用/撤回、SQLite 保存、过期页面保护。撤回不会消除故障，原计划只作参考。后续顺序：紧急订单及时间变化 → 配置数据导入 → 更大规模求解器 → LLM 结构化及追问 → 实际执行回执。先保住货物流向与历史执行状态，再增加异常类型。
