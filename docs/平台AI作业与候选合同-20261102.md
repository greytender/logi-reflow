# 平台 AI 作业、候选与规则草稿合同

2026-11-02。本合同对应 `agent_jobs.py`、`platform_agent.py`、`deepseek_agent.py`、`agent_actions.py`。网站通过平台自身后端使用 DeepSeek，不依赖开发工具 Codex，不等于集成 DSH runtime。

## HTTP 接线

根服务采用 `/api/multiwarehouse/agent/start`、`agent/job`、`agent/cancel`、`agent/apply-rules` 路径。端点需沿用本机来源校验；服务端不接受用户传入模型 URL 或 Python 代码。

- 发起：`JobRegistry.start(task_id, revision, message, planner=planner, selection=selection, request_id=request_id)` 返回 `{job, job_token}`。planner 必须在 HTTP 请求线程中创建，捕获当前临时密钥；后台线程不重新从浏览器会话读取凭据。
- 查询：`registry.get(job_id, job_token, after=0)` 返回 `{job}`。GET 令牌使用 `X-Agent-Job-Token`，不把 DeepSeek API Key 放在 URL。`after` 是最后收到的事件序号。
- 停止：`registry.cancel(job_id, job_token)` 返回 `{job,cancel_accepted}`；POST body 提供作业令牌。
- 应用规则：`agent_actions.apply_rule_draft(store,id,revision,run_id,reviewed=True)` 返回更新后的任务；根服务补充 `state=mw.view(task)`。必须以当前修订、草稿输入修订及内容指纹核验，不直接信任浏览器传来的旧完整输入。

`selection` 只允许 `warehouse_id`、`vehicle_id`、`order_id`，编号必须属于当前批次。`request_id` 可选，用于拒绝重复提交，不能代替作业令牌。

## 生命周期与恢复

状态为 queued → running → committing → completed；失败是 failed，中途停止经过 cancelling → cancelled。服务重启未完成的作业标 interrupted，不自动重新调用付费模型。若任务已按 operation_id 保存而作业最后一笔写入中断，恢复时会识别已保存的结果。

真实事件为 queued、model_started、model_completed、tool_started、tool_completed、tool_failed、answer_delta、committing、completed，以及 failed/cancelling/cancelled/interrupted。事件带 `seq/type/title/created_at/details`，不提供虚构百分比。`answer_delta` 来自 DeepSeek SSE 内容帧，不使用计时器模拟打字。

完成时 `job.result={task,state,agent_run}`。任务修订与候选以最终提交为准；正在流出的解释不能当作已保存结果。

每批次同一时刻只允许一项活动 AI 作业，同一注册器总并发上限8。任务被人工或另一个入口修改时，原作业在 CAS 提交阶段失败，不能覆盖新内容。每项作业使用独立随机令牌，数据库只保留哈希，查询和停止都校验它。浏览器可以保存作业编号、令牌和事件游标以恢复；这些不是 DeepSeek 密钥。

停止采用协作取消：等待当前 HTTP/计算调用返回后，在进入下一步或提交前检查停止状态。运行中不承诺瞬间中断供应商网络请求，也不承诺取消已发生的 Token 费用。进入 committing 后不再接受撤销保存；不论何时停止都不会撤回已有签收或回收事实。

## 模型与数据

默认官方 `deepseek-flash`，JSON 规划关闭深度思考，解释使用真实 SSE。首轮读取任务统计、是否存在方案/执行事实、最近三轮对话、显式选中业务对象。构造模拟任务可给路线编号；企业声明任务只给显式选中车辆的路线，不发送全量原始订单表、地址、道路矩阵或回执备注。业务计费规则可作为配置上下文。

模型只能选择白名单工作流，最多4项。dispatch、remaining、adjust、rules 单次至多一种；模型输出需要解析和后端业务核验。凭据不存入任务、事件或导出，供应商 HTTP 错误正文不进入用户响应。主动作业完成后保留实际 Token 用量；没有用量字段时不编造金额。

## 业务工具

- inspect：检查批次输入和业务状态。
- dispatch：按明确仓库归属求解候选，经独立核验后保存，不确认。
- compare：当前候选与简单追加基线对比，只有服务集合完整一致时给费用差，不把算法基线称为企业人工计划。
- risks：提供具体未安排/执行预警及能力缺口。声明了有限装载模型的仓库采用其当前核验状态，不一律称未检查；仍不证明冷链、回收箱几何或现场安全。
- remaining：已有人工确认与执行变化后，为原车剩余任务生成候选，不采用、不转移货物或抹去事实。
- adjust：明确订单/车辆的调车或同车调序，保留每个任务恰好一次，禁止跨仓移动，核验容量、时窗、回收、准入；有 loading_profile 时也调用有限几何与独立核验。生成 `agent_adjustment` 候选，不确认。已有执行事实禁止改原车货物归属。
- rules：生成计费参数或预计纸箱/周转箱数量的草稿；原输入不变。`agent_run.result.rule_draft` 包含完整规范化 data、逐项 changes、输入修订和指纹。人工应用后旧方案失效，需重新计算；过期草稿拒绝应用。

不能通过模型直接确认候选、写真实签收、改实际回收、企业派单、获取实时 GPS/路况或完成正式结算。

## 验证

专项：`python -X utf8 -m unittest discover -s tests -p test_agent_jobs.py -q`（10项）、`test_platform_agent.py`（6项）、`test_deepseek_agent.py`（8项）。覆盖作业令牌、实际工具事件、并发和版本冲突、停止不提交、重启恢复、规则应用与过期拒绝、明确路线调整、企业数据边界、SSE 解析以及跨流式块密钥脱敏（先缓冲再发布，不把分段密钥写入事件）。

真实付费联调：`scripts/verify_agent_jobs_live.py`，只用构造模拟任务。2026-11-02 三场景通过：排车及风险（155个SSE块，1966 tokens）、选中车辆调序（118块，2251 tokens）、规则草稿（62块，1932 tokens）。合计6149 tokens；确认状态始终为空，规则草稿未改原输入。证据在 `outputs/deepseek-agent-qa/jobs-live-verification.json`。这些结果不能用于声称真实企业节省、正式接入或现场履约。
