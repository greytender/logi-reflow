# 主工作台物理装载与未安排诊断

本轮在多仓工作台的主候选计算、人工调序与确认中接入已有有限三维装载构造和独立核验。它是对原先仅重量/总体积检查的补充，不是冷链、现场安全或企业收益认证。

## 可选输入

每个 warehouse 可提供 `loading_profile`，字段沿用 `loading_v1`：

```json
{
  "schema": "loading_v1",
  "data_kind": "simulated",
  "vehicles": [{"id": "WH_1_TRUCK_1", "length_cm": 240, "width_cm": 160, "height_cm": 160}],
  "items": [{"order": "WH_1_STORE_001", "sku": "STANDARD_BOX", "length_cm": 60,
    "width_cm": 40, "height_cm": 30, "rotate_base": true, "fragile": false, "max_top_load_kg": 70}]
}
```

车辆与订单/SKU必须覆盖该仓完整集合，不能只填示例中的一车一行。逐箱数量和重量读取当前订单明细，不重复输入。尺寸需为整厘米，体积须与明细每箱体积一致，不能按总体积反推尺寸。来源声明需与仓库一致。每仓最多80箱、有限200000次放置检查预算；每仓任务/车辆上限仍为12/4，不把全量企业附件宣称为已求解。

没有 profile 的旧任务可继续使用，结果明确为 `NOT_CONFIGURED`，不声称物理装载已核验。显式 profile 属于输入指纹；更改需要重新计算、核对和确认。已有执行事实后禁止修改原输入。

## 输出与界面

- `result.loading_verification.status`：`NOT_CONFIGURED`、`INCOMPLETE` 或 `VERIFIED_WITHIN_MODEL`。
- `boxes / checked_boxes / work / boundaries`：输入总箱数、已安排箱数、实际检查次数/预算与建模边界。
- 每车 `route.loading.placements`：`id,x,y,z,dx,dy,dz`，单位厘米，箱ID为`order/sku/箱序`，尾门在+x方向。
- `load_steps` 与 `unload_steps`：可按箱坐标逐步展示装卸；后者按门店列`order,box_ids`。
- `audit / instruction_audit`：逐箱几何和步骤中间状态的独立核验。确认候选前直接重审已保存坐标/步骤，不凭此前的passed标记放行。
- `result.diagnostics`：每个未安排任务的逐车检查，区分无准入、正向容量、窗口或收班、回收容量和单独可行；最后一类不表示组合路线可行。

优化主流程联合调用路线评价和装载构造；有限装载搜索未找到不能宣称无解。只有可用朝向下逐箱超出车厢等严格几何下界才标 `PROVEN_GEOMETRY_INFEASIBLE`。手工调序也生成新的坐标和步骤，继承原版本用于比较，不能绕开装载检查。

## 执行边界

确认后子任务保留原 profile 与坐标。剩余改序按当前剩余配送箱、原车和原坐标重新核验；受阻时拒绝候选/采用，要求人工确认倒货步骤，不自动重摆在途货物。此保守实现未实现允许倒货的动作规划。

回收包装仍按逐站重量与总体积检查，不含其实际几何摆放。冷链温区与共享冷链箱仍缺设备/箱规/监测合同，本模型不检查温度合规。轮包、轴荷、制动稳定、装卸人员通道和实际装卸时长也未建模。

## 构造样例与验证

`multiwarehouse.sample(physical_loading=True)` 提供两仓、6任务、12箱的小型明确构造样例。与企业116行附件无数据来源关系，不能称企业全量或真实履约验证。

专项测试 `python -X utf8 -m unittest discover -s tests -p test_warehouse_loading.py -v` 覆盖：有无箱规状态、主候选/确认、缺项和体积不一致拒绝、几何反例改用车辆、确定超尺寸保持未安排、坐标篡改阻止确认、人工调序重核验、原摆放在途改序和分类诊断。
