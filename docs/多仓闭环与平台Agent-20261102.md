# 多仓配送闭环与平台内 Agent 工作流

本轮按用户指定顺序推进：先多仓闭环，再精简现有风格工作台，接着接入平台内部工具工作流，最后评估算法增强。没有迁移框架、配置模型供应商或连接企业派单接口。

## 操作入口

运行 `python server.py` 或双击启动文件后打开根路径。左侧新建双仓模拟批次，依次完成“准备数据 → 核对方案 → 执行交接”。已有单仓任务从顶部“原单仓任务”进入，原数据没有迁移或覆盖。

1. 核对各任务和车辆的仓库归属、SKU箱数与单位、预计回收、容量、收货时间、费用规则及有向道路。详细规则在折叠区。支持多仓 JSON 导入；原始 Excel 核对草稿仍不能直接创建调度任务。
2. 保存并计算。各仓独立调用既有启发式算法，批次统一核验：全部任务恰好归于已安排或未安排，车辆不重复使用。超限、归属缺失、道路缺向或未知字段明确拒绝，不截取或静默丢弃。
3. 核对费用、利用率及未安排原因。可在同仓车辆间手动移动任务、调整顺序；调整通过时间、重量、体积、回收和车辆准入核验后形成新候选，展示调整前后费用与里程，须重新确认。不允许借此隐式跨仓调拨。
4. 勾选核对后统一确认。任一仓仍有未安排任务时整个批次不可确认。确认仍是本机操作，不等于企业系统派单。
5. 逐车按下一站填写完成时间、来源和实际回收数。实际数量与时间初始为空，不把预测自动签成事实。模拟输入只能录模拟回执；人工录入须说明来源，真实性待核对。
6. 保存返仓交接。回执保留不回滚，已有任一仓执行事实后锁定整个批次原输入及原方案。位置/等待记录只支持原车已知节点，更新剩余预测；不会自动签收或重排。异常时可生成同车剩余改序候选，人工采用时再次核验是否过期。
7. 导出当前已确认配送 CSV 或完整 JSON 交接包。CSV车次费用只在该车首个任务行填写，避免重复求和。JSON包含原始方案、回执、观察、剩余预测与工作流记录，始终标为 `not_sent / not_connected`。

## 多仓输入与算法边界

`schema_version` 为 `logireflow.multiwarehouse.v1`。顶层只接受 `warehouses / orders / vehicles / legs / schema_version`。模拟模板见 `examples/multiwarehouse-small.json`，网页下载入口也提供同一结构（API响应可能包在 `data` 内，导入支持该形式）。

每仓包含稳定 `id`、显示名 `name`、单仓 `settings`，可选本仓 `business` 费用和包装规则。订单与车辆必须显式提供 `warehouse_id`；配送任务ID与车辆ID各自在整个批次唯一。一个任务表示一次整店配送；同店由两仓供货必须先明确成两个独立配送任务，不按名称自动合并。各仓ID、任务ID、车辆ID需先映射为当前合同允许的稳定标识，原企业字段不能随意附加后被忽略。

道路为各仓仓库与该仓任务节点之间完整的有向矩阵。跨仓方向、未知节点及自环均拒绝。车辆只能访问本仓准入任务，从本仓出发并回本仓。每车一趟，不共享车辆，不推断库存、不自动分仓或跨仓调拨。最多8仓，每仓12任务、4车。该边界是有界试算范围，不是生产吞吐承诺。

当前只是按明确归属分组求解后统一闭环，并非联合决定库存分配、跨仓流量和共享运力的多仓全局优化。先保留原算法；需要增强什么由真实输入失败、人工修改记录、运行规模与同批对照决定。

出发载重利用率 = 已用车出发货重合计 / 已用车可用载重合计；容积利用率同理。每车另列含预计包装回收的沿途峰值。总体积核验不证明箱体摆放、堆叠、倒货或装卸通道可行，不能把这两个指标直接等同于材料中“装载率90%以上”。

## 平台内部 Agent 工作流

运行代码为 `platform_agent.py`，属于物流平台服务端，与开发工具Codex无运行依赖。网页下方折叠“平台 Agent 工作流”提供五个可执行本地入口：检查批次、检查并生成排车候选、解释费用与利用率、业务风险与缺口、生成剩余路线候选。

排车工作流真实执行 `检查输入 → 各仓求解 → 独立核验 → 比较与解释`，生成候选；剩余路线工作流保留执行事实和原车货物归属。工作流记录工具名、执行状态、耗时、输入修订及指纹、输出修订，随批次原子保存；并发旧请求被CAS修订保护拒绝。后续任务变更后，页面提示旧工作流结果需要刷新。

当前模式是 `platform_local_workflow`，`model_connected=false`、外部请求关闭。自然语言自主编排尚未接通，文本框禁用；不会用关键词匹配冒充大模型理解。没有预填供应商、模型、API地址或密钥，也不复用原演示的DeepSeek配置。

未来接入点为服务端注入 `AgentWorkflow(store, planner)`，规划器合同：

```python
planner.plan(context={...}, message='业务请求', tools={...}) -> ['dispatch', 'risks']
```

返回1—4项白名单工作流；单次最多生成一类候选。规划器初始上下文只包含任务ID、修订和检查摘要。确认方案、人工路线编辑、采用剩余候选、保存回执/观察及企业派单不在模型工具白名单内。当前HTTP入口没有注入规划器，也不接受客户端传入URL、代码或密钥。规划器单元测试使用本地替身，不是外部模型连接验证。

用户提供接口协议后，仍需实现供应商适配、超时/重试、请求和响应校验、企业数据传输范围、模型工具执行评估，再开启自然语言流程。只提供API Key不能自动完成企业数据、库存、车辆、路况与派单系统接入。

## 业务重点与证据边界

来源为用户2026-11-02提供的两张业务截图，原图保存在 `evidence/business-dispatch-source-20261102.png` 与 `evidence/business-priorities-source-20261102.png`。截图是业务现状材料，不是本系统测量结果。

| 业务重点 | 材料描述 | 当前可运行部分 | 未完成部分 |
| --- | --- | --- | --- |
| 优化排车与人工重排 | 10辆车人工排车熟练工约1小时、普通工约2小时；尺寸规格或实际偏差引发重排 | 按明确仓属排车、同仓人工调整候选、执行后同车改序 | 真实人工基线复核、复杂配载经验、跨仓共享运力、多趟 |
| 成本 | 双系统，部分运距与门店数需人工输入，公里预先固定 | 车次费用分项、方案前后比较、统一导出 | 4.2米车GPS、实际运营公里、TMS公里口径、正式结算 |
| 装载率 | 人工配载，材料称90%以上；司机装卸 | 重量/总体积、逐站先卸后收、预计回收峰值 | 真实箱体尺寸、规格、堆叠、卸货顺序/通道、现场验收 |
| 风险预判 | 缺实时路况感知和风险路段规避；装车排队，到货需人工通知 | 静态时间/容量预警、人工位置/等待、剩余预测 | 实时路况、风险道路来源、自动避险、到货通知、排队资源调度 |
| 逆向整合 | 空周转箱及退货纳入路线以减少空驶 | 空包装预计回收、实录回收、返仓交接 | 商品退货重量/体积/品类、接收仓、兼容规则及反向订单 |

减少人力成本是目标，不是已证收益。验收建议用同一批订单、相同业务约束和完整服务集合，记录：人工有效操作分钟、总历时、输入/核对/调整次数、未安排及风险项、费用试算与真实结算差异、装载失败及现场返工。工作流毫秒耗时不能冒充调度员节省时间，构造样例的费用差也不能冒充企业降本。

## 存储与验证

多仓批次在现有应用SQLite中使用独立 `multiwarehouse_tasks` 表，所有仓库、候选、执行子任务及工具运行记录作为一个文档以修订CAS更新。旧 `application_tasks` 不迁移、不覆盖。已有执行事实后锁定批次，是保守的一致性边界，后续如需仅锁单仓应单独设计。

专项测试：`python -X utf8 -m unittest discover -s tests -p test_multiwarehouse.py -v`；平台工作流测试：`python -X utf8 -m unittest discover -s tests -p test_platform_agent.py -v`；全量：`python -X utf8 -m unittest discover -s tests -q`。

本轮没有增强求解器，没有完成真实企业订单全量求解、物理装载、真实模型、GPS/路况、正式派单或人力节省效果验证。
