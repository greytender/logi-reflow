## 解决什么问题

车辆已出发，门店追加订单、改变收货时间或车辆故障时，调度员需要知道：哪些已送不能动、货在哪辆车上、新货去哪里取、剩余任务怎么改、迟到和费用如何变化。

本原型将“业务消息 → AI提取与补问 → 人工核对 → 本地约束算法 → 候选 → 采用保存 → 模拟执行 → 下一次异常”接成一个最小闭环。主要用户为配送中心调度员。目标是减少重复核对和不可执行的调整；尚无企业实测证明节省了多少时间或费用。

## 本轮：分步配送回执（2026-10-11，本地改进）

新建网页场景默认使用“到达 → 开始卸货 → 完成签收”三个**人工模拟回执**。推进时间或采用候选不会自动签收。货物在签收前仍归原车；当前到店任务锁定，签收后才继续。旧场景原样保留并标注旧规则，不能转换成真实签收证据。详见[分步回执验证](evidence/分步回执验证.md)。

小例子：新建模拟 → 时间08:10并推进 → V1确认模拟到达（S05）→ 时间08:12并开始模拟卸货 → 时间08:17并完成模拟签收。08:16签收会被拒绝。当前仍是12店3车模拟；可导入CSV尚未接入此流程，真实司机回执未接入。原下方P1→P2→P3数值属于旧规则演示，不代表新回执场景。

## 已完成与范围

2026-10-11补充：新增[企业离线试算入口](docs/企业离线试算入口.md)，支持CSV订单/车辆/有向道路表、门店多SKU汇总、卸货时间、车辆班次及到店准入。已运行30店300SKU行与8组构造情境，详见[本轮验证](evidence/企业离线试算验证.md)。它是出发前离线排程，尚未接到下述0.8连续异常网页；新增后77项测试通过。模拟验证不能表述为企业落地效果。

- 3辆车、12家门店：自动分配订单、访问顺序，检查重量、体积和收货时间窗口。
- 独立故障试算：保留已交付历史与健康车原货；救援车先到故障点接货8分钟再送。连续场景暂未接入故障。
- 紧急单：现有门店新增独立E01，货在仓库，接手车回仓装货8分钟；沿途检查容量，原车货物不随意换车。
- 收货变化：调整原车尚未交付顺序；已交付订单禁止改写。找不到完整方案时保留其他工作与未交付原货，候选禁止采用，需人工处理。
- 连续场景：一个E01后继续处理原订单收货变化，保存订单、车辆、货物归属、模拟位置、已交付节点、事件和计划版本。刷新和服务重启可恢复。
- 候选、采用、模拟执行分开；推进执行使未采用候选失效。修订号保护过期页面与重复采用，不撤回已经发生的配送。
- 采用前逐单核对事件、窗口、ETA、迟到与回仓装货，勾选核对后才可采用；刷新、重算或执行变化会清除勾选。不完整候选不能采用。
- 可放弃尚未采用的候选，保留版本与原因，已采用和已执行配送不回滚；只读查看最近20个场景及其中全部版本。
- 同一连续收货事件的两方案对照，网页显示路线、ETA、迟到、费用、改动订单数、求解时间，支持下载场景JSON。
- DeepSeek真实接通：调用名`deepseek-flash`。本轮10条构造消息达到预期提取/补问/拒绝行为，不能表述为总体准确率100%。

## 本机运行

Python 3.10+，运行代码仅使用标准库与浏览器原生功能，无第三方Python运行依赖。首次运行自动建立本地SQLite。端口仅绑定127.0.0.1。

```powershell
cd logistics-demo   # 如果仓库根目录已经是本项目，跳过此行
python server.py
```

在Chrome打开 http://127.0.0.1:8766/normal.html 。默认订单、车辆与费用都是模拟数据。已运行时不要重复占用8766端口。

AI可选；未配置密钥时，结构化表单和算法仍可使用。

Windows下：自行创建DeepSeek密钥并复制，在PowerShell 7执行`./configure-key.ps1`，脚本从剪贴板读取并用当前用户DPAPI加密保存到项目外`%LOCALAPPDATA%/LogisticsDemo/deepseek-key.dpapi`。随后用`./start.ps1`启动，密钥只注入服务进程。

也可自行在服务端环境设置`LOGISTICS_DEEPSEEK_API_KEY`。默认模型`deepseek-flash`，可通过`LOGISTICS_AI_MODEL`覆盖。不要把密钥写入代码、页面、README或仓库；不要求把密钥发到聊天。启动脚本不会读取其他工具的凭据。

## 旧规则P1→P2→P3例子（旧场景或脚本复现）

1. 点击“保存正常计划，开始新模拟”：建立08:00已采用正常计划P1。
2. 使用紧急单默认值：08:25、S07、10箱、承诺09:00、截止11:30。生成候选P2，在核对区检查回仓取货、ETA及迟到，勾选核对后点击采用保存。
3. 将“模拟执行到”设为08:26，点击推进。
4. 使用收货变化：08:26、S08、新开门09:15、新承诺09:30、新截止11:30，生成基于P2的P3。
5. 阅读核对区与对照表，勾选核对后采用P3。刷新网页、重启服务仍能读回；下载记录包含事件、版本和执行状态。
6. 不想采用时点击“放弃候选，保留记录”；在历史区选择场景和版本，只读查看。新建模拟将旧场景归档，不能用历史查看恢复或改写旧配送。

新建模拟保留旧场景。连续模式锁定基础货量与车辆容量；新建按钮使用加载的早上参考数据，后续编辑新场景基础数据的网页流程尚未完善。网页的早上参考区折叠显示，不代表当前执行计划。

## 架构与存储

```text
Chrome HTML/CSS/JS
  → 本地HTTP接口（server.py）
  → AI仅提取事件（ai_events.py）或结构化表单
  → 字段校验、人工核对
  → normal / urgent / timewindow / dynamic（有限启发式）
  → continuous.py（车辆状态、采用与模拟执行）
  → SQLite（场景、计划版本、事件、执行快照）
```

`data/sessions.sqlite3`仅本地运行，排除提交。旧`sessions`、`meta`记录保留，连续场景使用新增`dispatch_scenes`表；改动前SQLite备份保存在`data/backups/`，同样排除提交。每条路线保存时间、位置、累计里程、车上货物和完成节点的起点，后续模拟从起点继续，不沿新路线重放旧历史。

常用接口：`GET/POST /api/normal`；独立`POST /api/failure`、`/api/urgent`、`/api/window`；`POST /api/interpret`；`GET /api/ai/status`；`GET /api/dispatch`、`/api/dispatch/comparison`、`/api/dispatch/review`、`/api/dispatch/history`、`/api/dispatch/history/<id>`；`POST /api/dispatch/start`、`event`、`adopt`、`discard`、`advance`、`receipt`。历史、核对和对照只读；重放与已保存方案不一致时拒绝显示对照。网页勾选是人工操作提醒，服务端仍以修订号、候选ID及完整性校验为保护，不把勾选当成身份认证。

## 算法、数据与限制

正常分配采用多起点插入和有限移位；故障恢复采用有限分配/接货插入；紧急单搜索回仓与配送插入；连续收货变化检查原顺序和受影响订单在原车内的插入位置。优先比较未安排、迟到单数、迟到分钟，再比较费用加4元/改动单。有限启发式，无全局最优保证。

位置为平面直线示意，恒速30km/h；独立试算及旧场景到店视为交付；新连续场景使用三步人工模拟回执，卸货至少5分钟；仓库装货8分钟，暂无单独装货费用。费用含已行驶及未来行驶、最终回仓和出车固定费，不含真实人工、货损或完整企业成本。重量/体积总量检查不代表三维装载可行。

连续场景当前仅一个E01后原订单收货变化，异常时刻08:00–09:00，模拟执行可推进到当天24:00。尚未实现连续故障、多个紧急单、真实交通/GPS、司机回执、车载接入、账号权限、超过最近20场景的分页或实际通知；未验证大规模性能、真实企业效果、原创算法、行业首创或获奖概率。

外部依赖只有可选DeepSeek调用；只发送业务消息及最多4条补问原话，不发送订单全表、路线或密钥到网页。代码和网页可离线使用结构化表单。历史说明保存在[历史版本说明](docs/历史版本说明.md)，不得把其中“AI未接入”“无连续持久化”等旧状态当作当前结论。
