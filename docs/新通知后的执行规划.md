2026-10-11。依据用户转发的赛事补充通知调整；通知未独立核验发布渠道。10-11已用后台Chrome重新打开比赛物流全文，确认数据参考标为终赛提供；提交期限、渠道及条款仍需正式提交前核验。本文件为后续工作入口，历史记录保留。

最新业务依据与下一轮优先级见[公开业务调研与初赛改进](公开业务调研与初赛改进.md)。CSV-AI、检查点和只读执行交接已完成；继续补构造情境及人工任务验证，装载与调度衔接作为推荐题覆盖缺口单独评估。140项测试通过；行业独特性、企业收益仍待验证。

## 方向判断

继续AI＋物流城市配送，围绕一个问题做深：**车辆已出发，连续追加订单或改变收货时间时，怎样保留已签收事实和车上货物，生成可执行的剩余配送方案，并说明迟到、费用和改动的代价？**

按具体城市配送场景准备作品，用代码、约束与运行对照证明贡献。展示顺序调整为“业务异常 → 已发生事实与硬约束 → 两种处理方案 → 独立核算 → 核对采用”，界面用于解释证据。

题目已经提出运力匹配、路线优化、多约束配载、装卸协同与3D示意；这些需求本身不能作为本项目创新。我们选择其中的配送调度环节，新增出发后的连续事件与执行状态约束。当前没有覆盖完整智能配载题目，尤其没有3D装载、易碎/堆叠/冷链模型；总重量和总体积不能证明实际可装入车厢。应在材料中标明这个边界。

## 贡献与证据

| 题设需求/参照处理规则 | 当前新增的具体能力 | 实现与验证 | 能支持的结论 |
|---|---|---|---|
| 出发前分配车辆与路线 | 出发后依据当前道路段、货物归属及已签收历史调整剩余任务 | matrix_dispatch.py、continuous.py、CSV专项测试 | 保持已发生事实和原货归属；不是实时GPS调度 |
| 门店收货变化后保持原序等待 | 受影响订单在原车剩余序列内有限插入，比较费用与迟到 | contribution_benchmark.py的12组开门情境与4组硬截止情境 | 部分构造情境改善迟到，也有无变化、费用上升或不完整方案 |
| 紧急单在原序末尾回仓再送 | 在容量、准入及班次内枚举独立回仓取货和配送位置 | 同脚本12组第一/第二紧急单及超载情境 | 第二单可减少重复绕行；未证明所有紧急单都受益 |
| 只生成一次路线 | 候选、采用、模拟执行分开；回执锁定事实，过期候选失效 | DispatchStore、回执/连续/成熟化测试 | 防止旧状态覆盖新事实、不完整方案采用；不是生产可靠性证明 |
| 业务消息需要整理成字段 | DeepSeek提取、缺项补问、校验、人工核对；算法独立求解 | ai_events.py、csv_ai_events.py、真实构造样例 | CSV已接AI；小样本不证明企业消息质量 |
| 采用后的执行协同 | 从已采用货物与回执生成每单交接、等待和签收指标；预测失效隐藏旧ETA | dispatch_handoff.py、7项新测试与真实Chrome | 补执行逻辑与可审计导出；不是3D装卸或真实仓库回执 |
| 演示固定案例 | 四份CSV合同、多SKU、有向道路、班次和准入导入 | pilot.py、CSV网页流程及独立核算 | 提供离线迁移入口；还没有企业数据和真实司机接口 |

“参照处理规则”是可复现的简化编码规则，不是实测企业人工计划。不将取送货、时间窗、局部搜索或版本保存宣称为新算法；行业独特性和算法原创性尚未系统查新。

## 按顺序执行

### 第一步：收紧问题和材料口径（本轮已完成）

完成本规划、贡献表、README入口及比赛核对更新。保留旧版本证据，以当前状态入口为准。重点解释哪些能力是题设之外的实现增量，哪些仍未覆盖。

验收：读者能说清主要用户、触发异常、保留事实、算法改变了什么，以及未覆盖哪些题设要求；没有把模拟签收和模拟费用写成企业落地效果。

### 第二步：补同条件算法证据（本轮已完成）

新增 `python contribution_benchmark.py`：3/12店、两个固定种子，先人工模拟签收一单，然后对照开门延后、硬截止、第一紧急单、超载和第二紧急单。双方共用相同父计划、事件、道路、货物和历史；仅移除/保留局部插入搜索。第三单拒绝单独列为范围保护。

本次28个情境、56份方案通过独立核算，逐方法重放一致；20个情境指标无变化，8个有变化。4个开门情境减少迟到但增加费用，4个第二紧急单情境减少费用；16份方案不完整。无变化与失败不删除，不完整候选不能采用。28组配送集合相同；脚本仍禁止在配送集合不同时计算费用/迟到差额。

例：12店、seed20261011、延后60分钟，两边都安排12单；迟到68.84→0分钟，模拟费用595.09→633.24元，额外38.15元换取迟到改善。这是一次构造结果，不能推断平均收益。

验收：完整输入和两个输出可查；已签收不改、原货不换车、仓库货先取再送、容量/时间窗/班次满足；可重放；费用上升与失败保留。独立核算不调用路线求解器。报告见[新通知算法对照验证](../evidence/新通知算法对照验证.md)。

### 第三步：接通CSV异常与AI理解（本轮已实现并验证）

2026-10-11执行结果：已实现CSV专用合同、逐SKU缺项补问、准确编号校验、仓库取货确认、签收/卸货状态保护、前后修订校验，以及网页字段核对与候选采用。12条真实构造样例达预期；真实Chrome完成补问至4单签收/回仓；133项测试通过。原下方开发要求保留作为验收合同，证据见[CSV-AI连续闭环验证](../evidence/CSV-AI连续闭环验证.md)。当前实现依赖模型输出与人工核对，不能证明所有消息不发生幻觉；扩展质量与人工耗时仍待验证。

这项在规划时是主要缺口，本轮先补齐，再继续准备可交付检查点。

先定义CSV事件字段和状态合同：目的地只能选原始导入门店，订单编号与门店地址分开；多SKU箱数/箱重/箱体积不得猜；时间字段不得补造；两个紧急单上限、已签收订单与当前任务锁定由服务端校验。窗口消息和紧急消息分别处理，不通过AI暗改道路与成本。

先用固定响应验证提取、补问、编号消歧及服务端拒绝，再在授权的API用量范围内做小批真实调用。保留结构化表单作为降级入口。记录期望字段、实际输出、补问轮数、拒绝原因、调用延迟及可获得的用量；字段正确率与有效事件率分开，缺字段、多事件、越权提示和签收后改窗不能计为成功排程。

验收：同一CSV场景走通“自然语言 → 缺项补问/核对 → 校验 → 候选”，AI不会猜SKU或自主采用；真实调用和模拟响应证据分别标注。人工耗时改善需要另做任务实验，不能用模型延迟代替。

### 第四步：形成可交付检查点（已形成本地检查点，提交准备仍未完成）

已提供无密钥 `reproduce_csv_checkpoint.py`：3店与30店导入、已签收事实、两个独立紧急单、E02改窗、同条件对照、全程回执及回仓；每步独立核算和重新打开SQLite读取一致。30店32单/96条回执整段本机复现13.614秒，使用宽窗口构造数据和固定草稿，不代表AI或生产性能。真实AI端到端采用在隔离服务完成，失败/不完整情境由既有28组对照和测试保留。团队信息、最终提交规则、企业验证和外部同步仍未完成。

完成前述闭环后，复核现有正常排程、两个紧急单、收货变化和人工模拟签收；必要时扩大到30店连续异常。不能用30店离线排程或一次签收证明全程动态调度规模能力。

制作一个完整例子：CSV正常计划 → 签收事实 → AI整理一次消息 → 候选对照与代价 → 人工核对采用 → 后续回执 → 导出审计。同时保留一个无法接单的例子。演示与评审说明引用相同结果。

验收：新环境无需密钥即可运行算法与证据复现；AI依赖单独说明；代码、README、测试及演示主张一致。正式提交前补团队信息并核验最新规则。仓库同步遵循已有完整检查点节奏；本轮不做外部写入或比赛提交。

## 暂缓与待验证

暂缓：新增看板、装饰性3D图、更多紧急单额度、连续故障、跨车转货、新地址、拆单。连续故障会扩大执行模型与数据保护范围，待现有闭环及证据完成后再评估。

待验证：企业实际调度基线、业务约束、操作耗时、费用收益、AI在真实噪声消息上的质量、大规模连续异常性能。后续企业试点需取得脱敏订单、车辆班次/准入、路程时间表、事件与回执、人工计划及完整费用规则，先做离线回放。当前所有量化业务结果均为构造数据。

建议对外定位：**面向城市配送连续异常、带货物与执行事实约束的AI辅助调度原型**。AI负责理解消息，有限启发式负责路线候选，人工负责采用，独立核算提供可检查证据。
