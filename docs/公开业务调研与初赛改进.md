# 公开业务调研与初赛改进

2026-10-11。目标：利用当前公开资料，把城市配送连续异常原型放回企业已有流程中。公开页面用于确认业务形态，构造数据用于验证代码；两者不混用。未取得企业订单、内部SOP、人工调度或效果数据。

## 当前判断

主问题继续聚焦：**已有配送计划发出后，收到追加订单或收货变更，怎样在货物归属、当前道路段和签收事实约束内调整剩余任务，再把方案交接给相关人员？**

传化已经提供数字运输系统，官网历史案例也描述了TMS接单、路线优化、GPS可视与电子回单。作品应定位为现有系统旁的异常决策辅助模块。不能把“从人工到有看板”“首次做路线优化”当成我们的创新，也没有证据证明传化现有系统缺少动态重排。

推荐题目的装载、堆叠、易碎和3D指引尚未实现。这是覆盖范围的实质缺口。当前应清楚声明选择其中的配送调度环节，用可验证实现说明新增能力；不能把交接表称为3D装卸指导。未来若补装载，需要真实或明确构造的箱长宽高、车厢尺寸、朝向、支撑/堆叠、承重及卸货顺序，先做可行性校验再谈联动优化。

## 本轮已经实现的改进

新增dispatch_handoff.py和只读HTTP入口，从**已采用live_plan、保存的货物归属和人工模拟回执**生成交接，而非从页面正在展示的候选复制路线。

1. 每单列示门店、SKU/数量/箱重/箱体积、准入车辆、卸货时长、货物归属、采用车辆、取货批次和下一步责任角色。仓库货先取后送，候选新增货尚未采用时不出现在交接中。
2. 预测到达/完成与到达/卸货/签收回执分别列示。旧预测因延误无法通过约束时，交接隐藏全部剩余ETA；事实与货物归属继续保留，调度负责核查。
3. 区分已模拟签收数、按arrival/finish口径回执确认迟到数、过承诺但缺对应回执数。不能把“缺到达回执”直接说成实际迟到，也不能用安排单数代替签收单数。
4. 分开统计到达至卸货开始的等待和已签收卸货耗时。尚未卸货的等待累积到当前模拟时钟；该指标可能包含早到、门店等待和操作延后，不自动归责客户。
5. 导出带场景、修订号、采用版本、模拟标记、时间口径和事实来源的CSV。旧页面修订号拒绝导出；读取与导出不改变路线、候选或执行时钟。

这是业务逻辑与工程闭环的实现增量，没有新增优化算法，也不能宣称为行业首创。它补足“方案被采用以后，现场如何知道下一步、如何区分预测与事实”这一环。装货仍按每批8分钟模型推演，明确标为非仓库实绩；初始原货已装车也是构造假设。

## 初赛如何利用现有条件

现有证据分三类：公开来源说明为什么选择这个业务环节；构造数据验证约束和失败边界；已有真实DeepSeek构造消息验证小样本的提取/补问。三类证据不能相互替代。

展示一个连贯例子：多SKU CSV正常计划 → 一次追加新货 → 字段核对 → 候选与采用分开 → 仓库批次交接 → 到达但未签收 → 等待/卸货 → 下一次收货变化。加一个延误使剩余计划失效的反例，展示回执保留、旧ETA隐藏和人工接手。算法价值仍用现有28组同状态对照，保留无改善、成本上升和不完整结果。

30店300行SKU固定草稿复现只证明该构造案例的连续执行，不证明真实业务性能。无需等企业数据才编写正确的执行模型；也不能为了“更真实”给模拟数据贴企业标签。当前费用仅固定出车与里程，未含真实等待人工、装卸、返空、违约或货损成本。

## 下一轮优先级

第一优先：扩充可复现的公开背景构造情境，变化开门等待、卸货时长、班次与准入，把失败原因、同状态收益及交接一致性统一呈现；选择参数依据仍标为假设。

第二优先：用模拟任务实验测“读懂异常、核对字段、判断候选与完成交接”的耗时和错误率，比较结构化表单与AI辅助；先定义计时与计分，避免用API延迟冒充人工提效。

第三优先：调度与装载的可行性衔接。若选择补重点推荐题，先用明确尺寸的构造箱体/车厢做独立装载检查、卸货可达性及不可堆叠反例，不能先画装饰性3D图。真实规则到位后再替换参数。

决赛取得授权数据后：先核对订单、货物尺寸、道路、车辆班次/资质、事件、签收与完整费用合同；按实际事件时间离线回放，避免未来信息泄漏；与同一状态下的企业既有做法比较可行率、迟到、完整费用和人工耗时，再判断是否产生价值增量。企业收益、调度创新的行业独特性和生产可靠性目前均待验证。
