# 在途固定装载：状态与输入合同

2026-10-12，本地增量实现。只扩展CSV连续流程，不迁移旧场景，不做真实派单。

## 输入与创建

`POST /api/dispatch/start`原有`csv_files`可以增加`loading_profile`（与离线loading_v1合同一致）。完整联合路线、坐标与装卸审计通过后才创建独立人工模拟场景；缺规则、null、不完整布局、过期场景修订或已核对输入哈希不一致均拒绝，事务回滚。网页勾选只表示核对过模拟布局，不代表真实仓库已装车，也不是身份认证。

服务端从原始五份输入重新计算，不接受客户端提供的箱体坐标或自报“可装载”。`loading_input_sha256`由网页提交，绑定刚才核对的五份输入。有限搜索的耗时仍可能达到原装载预算；创建并不保证最优。

`fixed_loading.manifest`使用`fixed_loading_v1`，包含逐箱定义、车厢尺寸/载重、各车原始placements与原始配送顺序。`sha256`绑定完整manifest；`source_sha256`记录五份来源。哈希用于一致性保护，不是企业真实性证明或防恶意数据库管理员的数字签名。整个快照在候选、采用、签收、重启期间保持不变。

## 动态状态与不变量

现有anchor的`cargo`、`completed`、`pending`和`transit`继续作为执行状态。当前在车箱体 = 本车原始placements减去已签收订单箱体。到达与开始卸货不释放箱体；人工模拟整单签收才释放。没有部分卸货或部分签收模型。

收货变化仍在原车内移动受影响订单，保持当前道路目的地与当前到店任务。每条路线候选先核验原坐标，再核验有向道路、窗口、班次、准入与总载荷。`fixed_loading_check`记录本版本的当前坐标、卸货步骤、剩余箱体、错误及manifest哈希，并明确`coordinates_repacked=false`。

装载检查不调用构造求解器：按保存坐标重新检查边界、不重叠、朝向、单箱支撑链累计承重、易碎与尾门直线卸货，并逐箱移除、复核中间状态。尚未安排的原货仍物理存在，不通过从候选中删订单来删除挡路箱体。失败表示**该固定布局不支持当前候选顺序**，不是任意重新装车布局均无解。

采用前再次检查manifest与父计划一致、逐车原坐标仍能卸货；原有完整性、候选ID与修订保护继续有效。若时间预测因延误失效，保留回执事实；原摆放检查也在回执操作前执行。读历史不会推进状态。

## 新货与兼容边界

固定装载场景暂时拒绝所有紧急单，报“仓库新货剩余空间插入尚未实现”。不能沿用只检查重量/体积的8分钟取货流程，更不能回仓后免费重排原货。下一阶段须单独定义新增SKU箱规、剩余空间放置、装车中间状态、装货承诺时间与失败回滚，再开放这条路径。

没有`fixed_loading`的旧场景原样运行，仍只有重量/体积验证；原CSV双紧急单功能保留。连续故障、跨车转货、拆单、侧门/轮包、多人/叉车可达性、轴荷、温控与真实接口均未新增。

## 本机操作

在loading.html导入五份文件并联合试算，核对布局、勾选人工模拟说明，再点击“创建固定装载连续场景”。回normal.html刷新保存状态，使用收货变化、候选核对采用与三步人工模拟回执。连续区可展开原坐标和本版本卸货清单，场景JSON包含冻结快照。

构造反例五份文件在`examples/fixed-loading-three`。运行`python fixed_loading_benchmark.py`仅使用临时数据库，复现A→C→B被原摆放拒绝、采用A→B→C后9条回执并回仓。结果见`evidence/fixed-loading-benchmark.json`。
