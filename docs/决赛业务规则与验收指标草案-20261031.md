日期：2026-10-31｜状态：供本人审核，业务口径与数值目标尚待确认

## 1. 本阶段要解决的问题

面向传化现有订单业务，把配载、配送顺序、运费与空包装回收放在同一计划中计算，供调度员比较、调整和确认；在明确数据与建模假设的前提下，验证整批任务的履约、费用及调度工作量是否改善。用户已选择本阶段不纳入门店退货；主办方完整场景中的退货要求保留为后续差距。

用户与传化、动势资深项目经理交流后的重点为：装载率、物流调度、配送运费、纸箱回收，以及可嵌入现有订单系统的端到端业务与可视化交互。此处按用户转述记录，不将本草案视为业务方签字确认或开发承诺。

本稿只定义后续开发和验证依据。未修改算法、运行数据库、原始附件或既有证据；未完成真实系统接入、派单或企业收益验证。

### 3.1 交谈后采用的试算假设（2026-10-31）

单仓、车辆充足、统一当日完成、增量里程计费、允许倒货、仅回收可压平/套叠空包装，是用户本轮选择的简化范围；回收量到店确认并包括积攒空箱，是交谈中暂定的业务假设。这些均不能写成已经由主办方核实的现场事实。仓库地址待用户后续询问；不因“同一地级市”推定真实同仓，也不自动把不同区域归成同一批次。

用户授权未知包装回收空间按现有尺寸合理估计。实现时将压平厚度、套叠增高和容量预留设为可调整参数，至少对较小/较大回收占用做情景比较；原始尺寸推不出这些系数，不能伪装为实测。用预测量规划、实际回执核对，超预留情形必须明确提示待处置，不能静默丢弃回收任务。

冷链处理以主办方具体附件优先于用户对冷藏车的猜测。S3明确存在共享冷链箱，但未提供其尺寸；S2说明温控要求，并未确定实际车队采用全车制冷、局部温区或箱体保温/制冷的具体方式。试算使用显式配置与假设，真实冷链验收仍需设备、温度条件及记录支持。“一车1—3箱”是材料中的通常配置，不能硬编码为所有实例的箱数上限；每件冷链商品也不能直接当一个共享运输箱。

## 5. 算法目标：先保证业务可执行，再比较收益

以下是建议，目标顺序及任何权重均需本人和业务方审核：

1. 先检查数据与硬约束：配送任务不遗漏/不重复、同店不拆车、车辆容量、已确认的窗口及冷链/装卸规则、回收后的沿途载荷。
2. 在同一配送与回收任务集合、同一规则下比较总计费费用，并同时报告车次、里程、签收时效及装载情况。候选不能通过少送、漏收或放松约束获得“改善”。
3. 指标冲突时输出可解释的候选取舍，由调度员选择；尚未确认优先级时，不用任意加权总分冒充业务最优。
4. 保留无改善、费用上升和不完整结果。有限搜索未找到不等于数学无解；“更低费用”也不等于全局最优。
5. 根据用户最新选择，倒货由“一律禁止”调整为“允许但计算额外搬运”，不能再把原摆放下受阻直接当作整体配送不可行。必须形成可执行的移出、取货、放回步骤并核验中间状态；空间、支撑与安全规则仍适用。真实倒货工时和费用缺失时，用明确标注的次数/时间代理比较，不称为实测成本。

装载率不能单独最大化，否则可能增加绕路、压缩回收空间或影响时效。配送与回收须在各作业节点分别核算：作业后载荷＝作业前载荷－已确认卸下量＋已确认收回量；共箱、套叠与共享包装变化还需对应的实体包装模型。

回收量未知时，分别标明预测、容量预留、情景假设和实际回执。可以验证不同回收情景下的风险，但不能把未提供的回收量设为0后宣称完成真实回收优化。

## 6. 验收指标及计算口径

| 指标 | 建议定义 | 比较与证据要求 |
|---|---|---|
| 配送完整性 | 完整安排的应配送订单/全部应配送订单；另列门店数 | 无完整订单ID时只报告门店任务口径，不能冒充真实订单级完整率；计划与实际完成分开 |
| 硬约束违规 | 独立核验容量、归属、时间、装卸和已确认规则，逐类列出违规 | 待采用的完整可行方案须无已核验规则违规；规则缺失标“未验证”，不计为0违规 |
| 装载率 | 分别列体积/有效容积与重量/额定载重；综合口径按S1取二者最大值 | 按车次展示出发、回收作业后的沿途负载及峰值；批次均值说明纳入车次，不混合成无法解释的单值 |
| 用车资源 | 唯一实体车辆数与总车次分别统计 | 一车多趟累计车次，不能把两者都叫用车数；多趟能力未实现前单独标注 |
| 配送运费 | 按确认的合同规则逐车次列里程费、门店费及其他项目 | 区分企业结算运费与承运方内部运营成本；无法取得的费用不当作0；同任务门店费若固定，不算作路线优化收益 |
| 路程与时长 | 有向道路里程、驾驶时间、等待/服务时间、回仓时间分别列出 | 保留道路矩阵来源和时段；预测不作为GPS实绩；总工时与最晚回仓时刻分开 |
| 签收准时率 | 承诺窗口内签收的应交付订单数/全部应交付订单数 | 实际验收用签收证据；离线预测或卸货完成代理需标注，不用到达时间替代实际签收 |
| 回收履约 | 已完成的已知应回收任务/全部已知应回收任务，另列件数、体积和重量 | 计划可安排、已装车和已回仓交接分开；任务总量未知则不计算完整回收率 |
| 调度工作量 | 数据准备＋计算＋人工核对＋修改至可执行的总时间 | 算法耗时单列，不能直接与人工全流程耗时计算节省率；记录操作人与熟练程度等条件 |
| 方案响应与稳定性 | 计算耗时、成功/不完整/失败/超预算、重复运行差异 | 性能数值目标待确认；记录硬件、实例规模、输入哈希、算法配置和随机种子（如有） |

S1所述人工装载率90%以上、10辆车排车约1—2小时，为业务方提供的现状描述，尚非我们对这批订单的可复现基线。不得直接据此计算本作品改善率。暂不承诺降低多少费用、提升多少装载率或几分钟完成全量3D。

## 7. 端到端流程与UI验收

目标流程：订单系统/文件输入 → 数据检查与补全 → 联合配载、路由、运费和回收计算 → 人工比较与调整 → 确认方案 → 装车 → 配送签收与回收反馈 → 异常处置 → 回仓交接与费用复核。

| 工作环节 | UI应支持的实际决策 | 可检查的行为 |
|---|---|---|
| 接单与检查 | 看清批次、门店归并、货物及缺失字段 | 能追溯原行；不确定数据有明确标记，不静默填补关键字段 |
| 方案比较 | 比较车次、容量、运费、时效和回收空间 | 地图、装载图、费用与核验引用同一候选版本；明确未安排任务与失败原因 |
| 人工调整 | 改变车辆、门店分配或顺序并观察影响 | 对变更重新核验；原方案与修改方案可比；违反规则时不能按可行方案确认 |
| 确认与执行 | 区分候选、已确认计划、预测与执行事实 | 状态推进使旧候选失效；重复操作不重复执行；装车计划不冒充现场装车确认 |
| 司机/装卸交接 | 看下一站、卸货清单、回收任务及异常 | 以角色呈现必要动作；模拟回执与真实回执在界面及导出中可区分 |
| 回仓与复盘 | 看未完成、回收交接及费用变化原因 | 实际与预测分列；任务未完成或证据缺失不会显示为全部完成 |

“直接嵌入现有订单系统”分三级验证：①文件导入导出；②按约定合同完成模拟API往返及错误处理；③经授权在目标系统完成真实读写、身份权限、重复/乱序、失败回退和端到端核对。前两级通过不能称为第三级完成。UI外观相似也不是集成证据。

## 8. 验证安排与通过条件

| 阶段 | 要取得的证据 | 可以得出的结论 |
|---|---|---|
| 数据可用性 | 原文件哈希、字段及单位核对、行映射、归并规则、缺失项和补充来源 | 明确哪些任务和指标可试算，哪些仍受缺失数据限制 |
| 算法正确性 | 独立核验；正常、满载、回收超容、冷链/装卸冲突、时间窗与计费边界案例 | 仅在已建模且已验证的约束下判断候选是否可行 |
| 同任务比较 | 企业同批原计划或人工重新排程、相同输入及规则；保留不利结果 | 企业基线齐备时评价增量；只有编码规则基线时只称算法对照 |
| 规模与交互 | 按实际选定区域/波次运行，记录预算、失败及人工操作时间 | 判断当前规模及用户流程是否可用，不外推全企业能力 |
| 业务回放/接入 | 业务人员核对、合法数据环境、事件当时可知信息及目标系统记录 | 区分离线回放、旁路建议与真实执行，不用历史未来信息帮助决策 |

正确性通过条件建议为：已选定任务完整核对、已验证硬约束无违规、费用可复算、输入输出可追溯、无改善与失败可见。实际降本、时效和操作效率的数值门槛另行确认，不先填写任意百分比。

## 9. 交谈后仍需确认的六组问题

1. 暂按单仓时，其实际地址在哪里？订单日期、批次和服务区域怎样划分？同名多行、名称含“推断”及缺少的运单/门店ID如何解释？
2. 常规/冷链尺寸与体积单位是什么？共享冷链箱实际尺寸、容量、温度管理和车厢配置是什么？可提供哪些车辆参数？
3. 空纸箱与塑料箱的折叠厚度/套叠增高和可回放的回收量是否可提供？到店才能确认、积攒空箱一并回收的假设是否与业务一致？

### 11.1 官方回应中影响产品定位的细节

1. **已有系统，具体项目的智能排线、配车和一装多卸尚未上线。** S1第2页明确客户TMS与传化云载TMS未打通、需要双系统操作，部分其他客户已全流程对接。因此本项目应补选定业务的决策及数据衔接缺口；不能泛称传化整个产品没有智能调度，也不应再造一套完整TMS。
2. **算费已有自动化，关键输入仍需人工。** S1第3页说现有系统自动计算成本，但云载中的运距、门店数由人录入，距离为预先固化的公里数；同页及第2页说明4.2米车缺GPS轨迹。可验证价值是减少录入、使计划与费用一致、支持复核。路线规划不能恢复不存在的真实GPS，也不能自动变成实绩结算依据。
3. **装载率已被业务方描述为90%以上。** S1第3页为现场经验陈述，S2第2页又以“装载率偏低”描述一般痛点，两者表述存在差异。需问同一口径、同一任务的体积率/重量率及基线。不能先承诺大幅提高已有装载率；可优先验证排车工作量、方案可执行性和费用取舍。
4. **司机、调度、客服已有分工与单据。** S1第1页：客户下单备货、传化调度排线配车、供应商司机扫码装车与签收、客服处理回单。第2页嵌入装车单可见客户ID、集货位、包装类别/数量和车辆/司机等字段。应争取沿用这些编号与现有动作，生成可核对的一车装车清单、门店交接及回收清单。图片中的真实个人标识不另行抄录或公开。
5. **常规运力为外包固定运力。** S1第2页将无人配送自营与其他外包固定运力区分。用户的车辆充足是假设；不能推定企业运力无限，亦不能用自有车辆全成本口径直接替代外包计费。
6. **15元/店含卸货及带回周转箱/退货。** S2第1页计费表明确包含这些服务；第5页强调门店门口交接。不能在合同运费中无依据重复加收一次回收费。可以记录搬运耗时或内部成本，但必须与合同计费分列。
7. **回收无预下订单仍需随当次任务回仓，并检查沿途容量。** S2第2、5页。可精细建模预测、预留、到店确认及剩余路线重算；不能将未知回收量默认为0。用户先不做退货属于范围收缩，不能宣称覆盖官方完整逆向业务。
8. **装车排队与到店服务会影响时间。** S1第3页提到等装车位、人工通知预计到达；S1第5页的卸货时长公式实际包含到达至签收这一段。S2要求服务时间计入路线。应区分驾驶、等待、搬运、签收，预测与真实扫码时间分开；缺现场数据时不能声称实时排队优化或已改善准时率。

### 11.4 建议优先完成的业务贡献

建议主线：**依托云载订单的城配联合排车、回收及计费工作台**。这里描述目标，不宣称当前已接入。

1. **订单可计算、可追溯。** 解析官方表格与约定系统导出，保留来源行，核对门店身份与批次，区分常规件、冷链商品、运输箱、回收包装；把需补的数据明确交给用户确认。贡献是减少重复录入和错误归并，输出经核对任务清单。
2. **同批任务联合配车排线。** 在真实确认或显式假设的运力/尺寸/窗口下，把同店订单交给同车，结合道路与装载能力安排门店，输出每车任务、配送顺序、车次、载荷、费用和未安排原因。先复用与改进现有启发式，用同批人工计划对照，按性能瓶颈再决定算法替换。
3. **运费跟着方案走，计费依据可核查。** 路线公里、TMS合同计费公里、实际GPS公里分字段；保留来源、时间和换算规则。每次人工调整后重算门店及里程计费，支持计划费用和结算依据核对。100公里分支仍须确认；不把地图减里程直接等同于已降运费。当前`pilot.py`路线评价及独立核验均按固定费＋公里费计算；后续须同步改求解中的候选评价、独立核验和UI费用明细，不能只改页面显示的金额。
4. **回收进入沿途载荷。** 估计折叠/套叠空间并做情景比较，按到店确认值更新已装回收包装，核算每段重量与体积以及后续容量风险，必要时生成供人核对的调整方案。未验证几何时只称总量可行；不宣称全量精确3D或未知回收必可全带。
5. **方案能被人使用、能回到原流程。** Agent帮助查数据、补缺项、整理规则、调用求解与核验、解释变化；调度网页展示数据来源、可调整参数与候选取舍，确认后输出沿用企业编号的装车、配送、回收、费用数据。已有司机扫码/客服回单继续由原系统负责，真实接口就绪后再验证闭环。

暂缓复杂商品自动分箱、全温控监控系统、实时GPS/路况采集、装车位排队优化、司机新APP、多仓、退货及大规模任意箱体精确装载。保留明确接口与差距，不用这些未完成能力描述当前贡献。
